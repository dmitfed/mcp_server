# Исследование реализации офлайн RAG

Решения ниже задают первую конфигурацию для реализации. Источники подтверждают
наличие интерфейсов и артефактов. Совместную работу выбранных версий, качество
извлечения и время выполнения проверяют на этапе реализации.

## R1. Debian 13, CPU и CUDA 13.2

**Решение.** Debian 13 amd64 и системный CPython 3.13 в обоих профилях.
Офлайн-приёмка выполняется без доступного GPU с CPU-сборкой llama.cpp
`b12359` (`b1b770d90`). Для ускорения собирается отдельный бинарник того же
тега с `GGML_CUDA=ON`, `nvcc` из закреплённого CUDA Toolkit 13.2.x и
`CMAKE_CUDA_ARCHITECTURES` под целевой GPU. Для 13.2.0 в проекте применяется
Linux-драйвер от 595.45.04. Для другого патча 13.2.x фиксируется драйвер,
соответствующий его release notes. Записываются модель GPU, compute capability,
память, драйвер, ядро, nvcc и реально выгруженные на GPU слои. NVCC 13.2
поддерживает целевые архитектуры начиная с `compute_75`.

**Обоснование.** NVIDIA квалифицирует Debian 13 amd64, а CPU-сборка этой версии
движка уже проверена для диалога ядра. Переносим два набора бинарных артефактов с
одними и теми же версиями моделей. OCR, анализ формул, парсинг и хранилища
выполняются на CPU в обоих профилях. CPU и CUDA сравниваются по условиям
приёмки и поведению интерфейсов, с допуском на численные различия оценок.
[Проверка ядра](../001-offline-mcp-core/research.md#первая-конфигурация-с-моделью) ·
[Установка CUDA 13.2.0](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-installation-guide-linux/index.html) ·
[Драйверы CUDA 13.2.0](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-toolkit-release-notes/index.html#cuda-driver) ·
[Архитектуры NVCC](https://docs.nvidia.com/cuda/archive/13.2.0/cuda-compiler-driver-nvcc/index.html#gpu-feature-list) ·
[Сборка llama.cpp](https://github.com/ggml-org/llama.cpp/blob/b12359/docs/build.md)

**Рассмотренные варианты.** vLLM и Ollama остаются возможными реализациями
локальных адаптеров. Для первой поставки выбран один уже используемый движок.
Установка CUDA и драйвера входит в подготовку GPU-стенда.

## R2. Локальные модели и контракты инференса

**Решение.** Отдельные процессы `llama-server` на loopback для эмбеддингов,
реранкинга, описаний и контрольного диалога. Основной обработчик остаётся
одноразовым процессом ядра, модели загружаются один раз при старте серверов.

Управляемый запуск формирует эффективный профиль эмбеддера из проверенных
артефактов, фактических аргументов процесса и настроек подготовки текста.
В alias `rag-embed-<profile_id>` используется SHA-256 полного канонического
профиля. Адаптер сопоставляет запись запуска с процессом и владельцем
слушающего сокета. Перед использованием нового процесса выполняются запросы
с контрольным текстом и сравниваются с эталонными векторами из ведомости.
Эталоны получены заранее на проверенной конфигурации и переносятся вместе
с допусками. Успех проверки атомарно фиксируется в закрытом каталоге
с привязкой к записи текущего запуска и проверенной ведомости. Поиск,
инициализация и публикация требуют действующей аттестации. Проверка смены
`pooling` использует отдельную тестовую ведомость с независимо полученными
эталонами при тех же весах и размерности. После успешной аттестации этого
варианта проверка подтверждает несовместимость старого поколения и
доступность поиска после `rebuild` из SQLite.
[Контракт запуска и профиля](contracts/rag-tools.md#локальное-управление-и-конфигурация)

## R3. Научные PDF и формулы

**Решение.** PDFium через `pypdfium2` даёт текстовый слой, размеры и рендер
страниц. Docling Standard `2.151.1` с локальными layout/TableFormer
извлекает порядок чтения, таблицы с ячейками и размещение рисунков. В первой
сборке применяются Heron и TableFormer Accurate.
Пригодность текстового слоя проверяется по страницам. Docling получает
диапазоны исходных страниц с пригодным слоем в режиме `do_ocr=False`.
Для остальных диапазонов используется `TesseractCliOcrOptions` с
`lang=["rus","eng"]`, `force_full_page_ocr=True` и локальными traineddata.
TableFormer получает текстовые ячейки из того же прохода Docling с
`do_cell_matching=True`. Источник текста ячеек на сканированной странице —
слова Tesseract, привязанные к её структуре таблицы. Непривязанное к ячейкам
распознавание остаётся текстом страницы, а пробелы в структуре отмечаются
как частичное извлечение. Привязка к исходному номеру страницы ведётся
отдельно для каждого диапазона. [Диапазоны страниц в Docling](https://docling-project.github.io/docling/reference/document_converter/) ·
[Параметры OCR и сопоставления ячеек](https://docling-project.github.io/docling/reference/pipeline_options/) ·
[Выход TSV Tesseract](https://tesseract-ocr.github.io/tessdoc/Command-Line-Usage.html#tsv-output)

Детектор PaddleOCR `PP-DocLayoutV2` выделяет оба класса формул на рендере.
`PP-FormulaNet_plus-S` распознаёт вырезанные области.
Формульный адаптер запускается с CPU PaddlePaddle `3.3.1` и
`paddleocr[doc-parser]==3.5.0`, веса загружаются из переданных каталогов.

Общая система для сопоставления — пиксели видимого растра PDFium с началом
в левом верхнем углу. Рендер учитывает `CropBox` и исходный `/Rotate`,
без дополнительного поворота. Координаты PDF преобразуются через
`PdfBitmap.get_posconv(page)` того же рендера. Для Docling преобразуются
четыре угла области с учётом объявленного начала отсчёта, размера страницы
и видимого прямоугольника. Результат пересчитывается в систему исходной
страницы и затем в общий растр. Если однозначно сопоставить системы
не удалось, объект отмечается как частично разобранный. Сырые рамки
Tesseract и PaddleOCR относятся к переданному им растру. Для вырезки или
масштабированной копии перед сопоставлением восстанавливаются смещение
и масштаб. Рамка ограничивается размерами общего растра. Геометрия живёт
в рабочем представлении разбора. В SQLite и MCP локатор PDF содержит
только номер исходной страницы. [Преобразования координат PDFium](https://pypdfium2.readthedocs.io/en/stable/python_api.html#pypdfium2.PdfBitmap.get_posconv) ·
[Начало отсчёта и размеры в Docling](https://docling-project.github.io/docling/reference/docling_document/)

Растровый рисунок сохраняется из PDF при доступном оригинале, для векторной
схемы сохраняется вырезка рендера.

**Обоснование.** Docling обогащает уже размеченные формулы. Отдельное
обнаружение inline и display покрывает формулы, для которых поиск только
по выходу Docling недостаточен. Формульные области привязываются к тексту
по пересечению с позициями слов. Совпавшие области Docling и PaddleOCR
объединяются, а класс `inline` или `display` берётся из PaddleOCR.
Неполное распознавание сохраняет визуальный артефакт и
фиксирует причину. Критический прототип проверяет отдельные идентификаторы,
номера страниц и математическую структуру inline и display. Для регрессии
используется гибридный PDF с цифровой страницей и сканом таблицы. На
контрольной странице заданы поворот на 90° и смещённый `CropBox`.
Проверяются уникальный текст и числовое значение в конкретной ячейке,
структура строк и столбцов, содержимое кропа заданной формулы или рисунка
и одно поле `page` в локаторе.
[Docling offline](https://docling-project.github.io/docling/usage/advanced_options/) ·
[Обогащение Docling](https://docling-project.github.io/docling/usage/enrichments/) ·
[Layout с двумя классами формул](https://www.paddleocr.ai/v3.5.0/en/version3.x/module_usage/layout_analysis.html) ·
[FormulaRecognition](https://www.paddleocr.ai/main/en/version3.x/module_usage/formula_recognition.html) ·
[Колёса PaddlePaddle](https://pypi.org/project/paddlepaddle/3.3.1/) ·
[PDFium Python API](https://pypdfium2.readthedocs.io/en/stable/python_api.html)

**Рассмотренные варианты.** Один преобразователь Markdown упрощает адаптер,
но плоская выдача теряет геометрию. MinerU поддерживает геометрию и формулы.
Выбрана композиция с явно управляемым OCR русского текста, форматами ячеек
и отдельной проверкой формульных регионов.
[Контракт результата MinerU](https://opendatalab.github.io/MinerU/reference/output_files/)

## R4. Word, Markdown и исходники

**Решение.** DOCX разбирается штатным ZIP и `defusedxml`. Связи OOXML
соединяют поля, встраивания и media с местом в документе. OMML хранится
структурно. Для DOC сохраняются байты исходного CFB, извлекаются хранилища
`ObjectPool` через `olefile`, а их место определяется по полям и
символьным позициям MS-DOC. LibreOffice headless в отдельном профиле готовит
нормализованное представление и рендер для сверки. Встроенные OLE-объекты
MathType и Equation Editor сохраняются отдельно от визуальной копии.
При отсутствии читаемого предпросмотра используется доступное исходное
представление и отчёт о потере.
[Стандарт MS-DOC](https://learn.microsoft.com/en-us/openspecs/office_file_formats/ms-doc/f7983581-d107-4a1f-b5f7-f3650e777c04) ·
[Формат OMML](https://learn.microsoft.com/en-us/office/math/mathml) ·
[Объекты MathType](https://docs.wiris.com/en_US/mathtype-support-notices-category/a-different-equation-opens-in-mathtype-than-the-one-double-clicked-in-word) ·
[Режим командной строки LibreOffice](https://help.libreoffice.org/latest/en-US/text/shared/guide/start_parameters.html)

Для встроенного рисунка DOC без поля формулы и OLE-связи берётся сам
рисунок или его читаемая визуальная копия с якорем в блоке Word.
Локальный визуальный классификатор из R2 выделяет изображения, на которых
самостоятельно представлена математическая запись. Для них формульный
распознаватель из R3 пытается восстановить структуру в LaTeX. При уверенной
классификации изображение сохраняется у объекта `formula` с собственным ID
и исходным якорем. Полный отчёт предупреждает об отсутствии нативной записи.
При неполном распознавании с этого ID по-прежнему доступно читаемое
изображение. Контрольный DOC содержит обычный рисунок и отдельно
уравнение, вставленное как изображение без поля и OLE-связи. Проверяются
тип `formula`, ID, положение в Word и доступное представление.
[Преобразование формул при сохранении в старом формате Word](https://support.microsoft.com/en-us/word/compatibility-changes-between-versions)

LibreOffice запускается в одноразовом профиле внутри Bubblewrap с отдельным
сетевым пространством. Конвертер получает на чтение снимок входного файла
и локальный runtime с нужными библиотеками и шрифтами. Профиль и выходы
пишутся во временный рабочий каталог. Каталоги корпуса и базы, секреты и
сокеты хоста в это окружение не передаются. Загрузка через локальный
UNO-адаптер задаёт `MacroExecutionMode=NEVER_EXECUTE` и
`UpdateDocMode=NO_UPDATE`, OLE-объекты обрабатываются как данные. Если
изоляция или эти настройки недоступны, преобразование прерывается с
диагностикой. В приёмке проверяются внешняя ссылка на тестовый ресурс
и макрос, записывающий маркер в доступный для записи рабочий каталог.
Содержимое ресурса отсутствует в результате, маркер отсутствует в каталоге.
[UNO MediaDescriptor](https://api.libreoffice.org/docs/idl/ref/servicecom_1_1sun_1_1star_1_1document_1_1MediaDescriptor.html) ·
[Режимы исполнения макросов](https://api.libreoffice.org/docs/idl/ref/namespacecom_1_1sun_1_1star_1_1document_1_1MacroExecMode.html) ·
[Режимы обновления связей](https://api.libreoffice.org/docs/idl/ref/namespacecom_1_1sun_1_1star_1_1document_1_1UpdateDocMode.html) ·
[Изоляция Bubblewrap](https://github.com/containers/bubblewrap/blob/main/README.md)

Markdown разбирается `markdown-it-py` с правилами GFM и
`mdit-py-plugins` для формул. Для ссылок принимаются только локальные
файлы под корнем корпуса. Код разбирается `tree-sitter` с грамматиками
Python, C, C++, Kotlin и QML/JS. Qt C++ сохраняет контекст сигналов и
слотов, Qt Designer `.ui` разбирается как дерево XML. Для `.h`
сначала применяется настройка пути, затем C++ по умолчанию.
Строки верхнего уровня и повреждённые области получают собственные
фрагменты с исходными координатами. Части одной декларации получают
общий стабильный `symbol_id`, вычисляемый в пределах `version_id` по
типу декларации и её байтовому диапазону в дереве. У перегрузок и
одноимённых деклараций с разными диапазонами разные идентификаторы.
У текстового фрагмента без надёжно определённой декларации поле
`symbol_id` отсутствует. Локальный комплект содержит собранные грамматики
и их ревизии.
[Список грамматик Tree-sitter](https://tree-sitter.github.io/tree-sitter/#parsers) ·
[Грамматика Kotlin](https://github.com/tree-sitter-grammars/tree-sitter-kotlin) ·
[Грамматика QML/JS](https://github.com/yuja/tree-sitter-qmljs)

**Рассмотренные варианты.** Преобразование DOC в DOCX используется как
дополнительное представление. Исходный объект и привязка сохраняются из
оригинала. Разбиение только по длине оставлено для участков, где дерево
не даёт надёжных границ.

## R5. SQLite и Qdrant

**Решение.** APSW `3.54.1.0` со встроенной SQLite, локальный WAL и
`synchronous=FULL`. Qdrant `v1.20.2` в нативном
односерверном режиме на loopback с выключенными gRPC и телеметрией. REST
используется через `httpx2`. Один физический набор точек на
поколение профиля. SQLite хранит активные версии и имя физической коллекции.
Точки пишутся идемпотентно с `wait=true`. Только после подтверждения
всех записей короткая транзакция SQLite публикует версию. Запрос берёт
согласованный снимок активных версий и передаёт их в keyword `match.any`
вместе с остальными фильтрами до лимита Qdrant. Базовый поиск использует
`exact=true`. Получение артефакта по ID читает только SQLite.

**Обоснование.** Полный перебор 10 000 векторов по 1024 float32 требует
около 39 МиБ сырых векторов. Пул из активных версий в одном корпусе
существенно меньше списка отдельных материалов. APSW закрепляет исправленную
ветку SQLite без замены системной библиотеки. Поиск держит разделяемую
блокировку обслуживания до завершения выборки Qdrant. Импорт и перестроение
держат её до коммита или отката публикации. Очистка берёт исключительную
блокировку и сохраняет готовую коллекцию, включая готовый пустой индекс.
[Протокол публикации](data-model.md#публикация-исключение-и-восстановление)
[APSW и встроенная SQLite](https://rogerbinns.github.io/apsw/install.html) ·
[SQLite WAL](https://sqlite.org/wal.html#the_wal_reset_bug) ·
[Qdrant v1.20.2](https://github.com/qdrant/qdrant/releases/tag/v1.20.2) ·
[Qdrant Match Any](https://qdrant.tech/documentation/search/filtering/#match-any) ·
[Qdrant Upsert Points](https://api.qdrant.tech/api-reference/points/upsert-points)

**Рассмотренные варианты.** Признак active в Qdrant пришлось бы атомарно
согласовывать с SQLite. Алиасы Qdrant применимы для других сценариев,
здесь физическое поколение переключается в одной транзакции вместе
с профилем. Аппроксимацию можно оценить при росте корпуса на сравнении
с точным отбором.

## R6. Поставка и измерения

**Решение.** На подключённом Debian 13 фиксируются wheels с SHA-256,
системные пакеты и языки OCR, бинарники CPU/GPU, наборы весов и лицензии,
грамматики и контрольные данные. GGUF загружаются через `hf download`
с полными ревизиями и сверяются с опубликованными SHA-256. Для всех
остальных артефактов версия или commit и SHA-256 попадают в ведомость
комплекта. Системный набор для Word включает Bubblewrap и совместимый с
LibreOffice системный `python3-uno`. Пакет и сборка проверяются без сети
на чистой системе. Рабочие процессы получают локальные пути и loopback
endpoints. CPU и CUDA проверяются в раздельных средах с привязкой
проверяемых портов к процессам запуска.
[Загрузка конкретной ревизии HF](https://huggingface.co/docs/huggingface_hub/guides/cli#download-a-specific-revision)

**Обоснование.** Контрольный CPU-стенд в плане — 8 физических ядер amd64
с AVX2, 32 ГиБ RAM и SSD. На 100 активных источниках и 10 000 уникальных
материалов проектные пределы — 45 с на один поиск с реранкингом и 3 с
на чтение одной части материала после готовности сервисов. Для индексации
документа начальный бюджет 900 с с единым MCP-дедлайном 960 с.
Реальные значения, пиковая память, оборудование и версии фиксируются
в отчёте. Отдельно измеряются векторный отбор и реранкинг.

**Рассмотренные варианты.** Загрузка по требованию упрощает установку
при доступном интернете. Для офлайн-сценария сборщик переносит полные
артефакты и проверяет комплект до развёртывания.
