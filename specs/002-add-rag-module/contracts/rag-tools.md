# Контракт модуля RAG v1

[Схемы входа и манифест](rag-module.json) · [Модель данных](../data-model.md) ·
[Контракт ядра](../../001-offline-mcp-core/contracts/module-v1.md)

Результат каждого успешного MCP-вызова — JSON-объект в
`structuredContent` и текстовом представлении ядра. Три операции используют
существующий транспорт Streamable HTTP. Значения `default` применяет
обработчик. Все пути относительны к настроенному корню. Обработчик
отклоняет выход из корня, символические ссылки, абсолютные пути, пустые
имена, недопустимые пути источника и непригодный текст запроса.

| Полномочие | Доступ |
|---|---|
| `rag.index` | Индексация, сокращённый отчёт и административные команды. |
| `rag.read` | Поиск и чтение материала, исходной версии, полных метаданных и сохранённого отчёта по ID. |
| Оба | Полный отчёт индексации. |

При отказе в доступе обработчик использует предусмотренный ядром
`PermissionError`. Ошибки обработки и зависимости возвращаются ядром как
`isError: true` с его сообщением. Безопасный код этапа модуль пишет в свой
локальный журнал. `tool_timeout` обрабатывается по контракту ядра.
Пустая выдача — успешный `{"matches":[]}`.

## Индексация `rag_index`

`file` задаёт один источник. Режимы обработки:

- `normal` переиспользует готовую полную активную версию того же снимка.
  Повтор частичной версии запускает обработку. Исключённый источник
  даёт статус `excluded`.
- `refresh` явно повторяет извлечение для не исключённого источника.
  Активность определяется фазой публикации и полнотой обработки.
- `publish` явно возвращает исключённый источник после успешной полной
  обработки нового снимка. Для активного источника используется поведение
  `refresh`.

Успешный ответ с одним правом индексации содержит только `status` и
`published` типа boolean. `status` принимает `published`, `reused`, `partial`,
`superseded` или `excluded`. Значение `published` относится к этой
попытке. Для впервые опубликованной частичной версии возможна комбинация
`"status":"partial","published":true`.

При обоих правах ответ также содержит `report_id`, `source_id`,
`version_id` для обработанной или переиспользованной версии,
`active_version_id`, `counts` по типам, начальный список `issues`
и число оставшихся замечаний `omitted_issue_count`. Поля версии,
которой нет, имеют значение null. Каждый элемент `issues` содержит
`code`, `kind`, `location`, `material_id` и `representation_ids`.
Для неизвестного типа, места или отсутствующего сохранённого материала
соответствующее поле равно null. `representation_ids` содержит ID всех
сохранённых представлений материала, доступных через `rag_get`, либо
пустой массив. Каждую пару `material_id` и `representation_id` можно
прочитать через `rag_get` с `view=content`, даже если материал не попал
в поисковый индекс.

По `report_id` клиент с `rag.read` может прочитать сохранённый UTF-8
JSON через `rag_get` с `view=report`. В нём те же поля, полный список
`issues` в исходном порядке и `omitted_issue_count: 0`. Значения
`status`, `published`, `version_id` и `active_version_id` описывают
зафиксированный результат данной попытки. В успешном ответе с обоими
правами `report_id` всегда ведёт к сохранённому отчёту, включая
случаи обрезки списка. Публикация и доступность отчёта фиксируются до
возврата ответа. Служебный журнал получает только коды и метаданные
из раздела диагностики.

## Локатор PDF

В `rag_search`, `rag_get`, полных метаданных и замечаниях отчёта
с известной страницей локатор PDF содержит ровно одно поле, например
`"location":{"page":7}`.
Значение `page` — целый номер страницы исходного PDF с отсчётом от единицы.
Материалы с одной страницы различаются по идентификаторам.

## Поиск `rag_search`

Оператор задаёт порог по умолчанию. Начальный профиль использует 0,0 и
пул из 32 кандидатов. `min_score` переопределяет порог в конкретном
запросе. Предельный размер публичной выдачи — 20. Фильтры `kind` и
`file` совместно действуют на согласованный набор активных версий
до ограничения пула. Недоступность готового профиля или Qdrant считается
ошибкой. После успешного отбора с пустым пулом реранкер не вызывается.

Для каждого кандидата требуется одна конечная оценка модели в диапазоне
[0, 1]. После реранкинга части одного материала объединяются по его
идентификатору, сохраняется лучшая часть. Сортировка идёт по убыванию
оценки, при равенстве — по порядку векторного отбора. Порог включительный.
Итоговый лимит применяется к уникальным материалам.

Ответ содержит `matches`. Каждый элемент содержит `id` материала,
`source_id`, `version_id`, `file`, `kind`, `location`, `score`
и `excerpt` с текстом, описанием либо табличной частью. Для кода
возвращаются доступные `language`, `symbol_kind`, `symbol_name`,
`scope`, `signature` и `symbol_id`. Части одной декларации в пределах
версии имеют общий `symbol_id` и собственные `id` и локаторы.
`excerpt_truncated` показывает сокращение выдержки, а
`truncated_fields` перечисляет сокращённые или опущенные поля
метаданных. Полный материал и метаданные читаются по `id`.

## Получение материала `rag_get`

Для всех режимов требуется `rag.read`. Активность версии для чтения
не требуется.

| `view` | Что передаётся в `id` | Результат |
|---|---|---|
| `metadata` | Материал или версия | Уместившиеся метаданные в JSON, полный список сокращённых полей в `truncated_fields`. |
| `full_metadata` | Материал или версия | Части сохранённых полных метаданных в UTF-8 JSON. |
| `report` | `report_id` | Части сохранённого полного отчёта индексации в UTF-8 JSON. |
| `content` | Материал или версия | Части двоичного представления материала либо исходного файла версии. |

Метаданные содержат `id`, `source_id`, `version_id`, `file`, `kind`,
доступные `location` и `description`, метаданные кода из выдачи при
наличии и `representations`. Элемент `representations` содержит
`representation_id`, `role`, `mime`, `size` и `sha256`. Для версии
`kind` равен `source`. В режиме `metadata` `truncated_fields`
содержит имена полей, сокращённых для передачи. Если список представлений
неполный, указан ключ `representations`. `full_metadata` содержит
полные значения и весь список, `truncated_fields` пуст.

При `view=content` для материала требуется принадлежащий ему
`representation_id`. Для версии читается исходный файл, параметр
`representation_id` отсутствует. В остальных режимах
`representation_id` не принимается. Для трёх режимов чтения частями
`offset` и `length` относятся к полным сырым байтам представления.
Выход каждой части содержит `id`, `mime`, `size`, `sha256`,
`offset`, `length`, `next_offset` и `data_base64`. У полных
метаданных и отчёта `mime` равен `application/json`. `length`
в ответе равен числу декодированных байтов части. `next_offset` —
начало следующей части или null на последней части. При смещении,
равном размеру, возвращается пустая часть с `next_offset: null`.
Смещение после конца и несоответствие ID выбранному режиму или
представлению дают ошибку. После объединения всех частей SHA-256
совпадает с `sha256` ответа. JSON декодируется после объединения
частей, поскольку граница может разделить многобайтовый символ UTF-8.

### Бюджет ответа

Внутреннее сообщение вида `{"result": …}` сериализуется как компактный
ASCII JSON с экранированием Unicode по формату ядра. Его длина в
байтах составляет не более 1 048 576. Обработчик измеряет этот размер
до передачи, включая поля, идентификаторы, Base64 и обёртку.
Максимальная сырая часть `content`, `report` или `full_metadata` —
128 КиБ до Base64, по умолчанию 64 КиБ.

Для кратких ответов применяются предварительные бюджеты
сериализованного размера. Одна запись поиска — не более 40 КиБ при
выдаче до 20 записей, а метаданные и начальный отчёт — не более
128 КиБ на ответ. Сокращаются только поля предпросмотра, включая
выдержки, описания, имена, сигнатуры, области видимости и полные
записи из списков замечаний и представлений. Выдержка также ограничена
2 000 символами. Строки сокращаются на границе символа, элементы
списка добавляются целиком, флаги сокращения учитываются в бюджете.
`published`, `status`, `report_id`, идентификаторы материалов,
версий и символов, путь, тип, оценка и локатор передаются целиком.
Канонический `file` при приёме источника ограничен 1 024 скалярными
значениями Unicode, что даёт не более 12 290 байтов для JSON-строки.
Локатор имеет отдельный бюджет 4 КиБ сериализованного ASCII JSON.
Он состоит из числовых позиций и коротких ключей, включая код части
документа для Word. Произвольные имена и пути передаются отдельными
полями. Обязательные поля записи поиска занимают менее 20 КиБ
при этих ограничениях, включая UUID, конечную оценку и обязательные
признаки сокращения. Это оставляет место для полей предпросмотра
в бюджете записи 40 КиБ. Полные значения доступны по тем же
идентификаторам через `view=report` и `view=full_metadata`.
Превышение объёма предпросмотра само по себе не приводит к ошибке
инструмента.

## Локальное управление и конфигурация

Рабочий процесс получает абсолютный путь `MCP_RAG_CONFIG` из окружения
оператора. TOML v1 содержит:

- `config_version=1`, `source_root`, `state_dir`, `diagnostics_path`.
- `[qdrant]` с loopback `url` и `api_key_file`. Ключ передаётся
  сервису из отдельного файла с доступом для сервисного аккаунта.
- `[inference]` с `embed_url`, `rerank_url`, `describe_url`,
  `artifact_lock` и абсолютным путём `runtime_dir`. Запись
  `runtime_dir/embedding-runtime.json` создаёт управляемый запуск
  из тех же настроек. Запуск берёт параметры эмбеддера, включая `pooling`,
  из доверенной ведомости. Каталог и ведомость доступны сервисному аккаунту.
- `[extract]` с `docling_model_dir`, `layout_model_dir`,
  `formula_model_dir` и `tessdata_dir`. Опциональная карта путей
  для выбора грамматики `.h`.
- `[limits]` с `max_source_bytes`, `max_pdf_pages`, `max_unpacked_bytes`,
  `pool_limit`, `default_min_score`, `index_timeout_seconds`,
  `search_timeout_seconds` и `get_timeout_seconds`. Предел пула больше
  допустимого лимита выдачи.

Инструменты принимают только относительные пути внутри одного корпуса.
Адреса служб, пути программы и к модели управляются конфигурацией
оператора. Сетевые запросы идут по loopback без внешнего proxy, URL
из документов и запросов обрабатываются как данные. Модуль пишет в
локальный журнал только время, имя операции, этап, фиксированный код
и при наличии служебный ID вызова. Оригинальные ошибки остаются вне журнала.

### Проверка эффективного профиля эмбеддингов

`profile_id` — полный SHA-256 канонического JSON объекта
`embedding_profile` в UTF-8. Для канонизации сортируются ключи объектов,
используются компактные разделители и прямой Unicode. Числа задаются
целыми значениями. Профиль содержит `schema_version`, `model_sha256`
включая токенизатор в GGUF, `llama_cpp_commit`, `embedding_mode`,
`pooling`, `context_size`, `tokenizer_options`, `query_instruction`,
`document_prefix`, `preprocessing_revision`, `normalization`,
`dimension` и `metric`. Алиас endpoint имеет вид
`rag-embed-<profile_id>`.

Контролируемый запуск формирует профиль по реально применяемым параметрам
и хешу весов. Параметры, влияющие на выход, задаются явно, в том числе
`--embedding`, `--pooling`, `--ctx-size` и `--embd-normalize`. Запись
запуска связывает профиль с хешем бинарника, endpoint, PID, временем
старта процесса и идентификатором слушающего сокета. Проверяются
фактические аргументы локального процесса и принадлежность сокета
этому процессу. Аналогичный алиас в HTTP-ответе подтверждает модель
ответа вместе с локальной проверкой запуска.

Первый preflight выполняется до инициализации корпуса. Он отправляет контрольные
тексты документов и запросов через тот же адаптер в режиме контрольных проб
и сравнивает компоненты векторов с заранее полученными эталонами из
доверенной ведомости в указанном там допуске. Режим контрольных проб
доступен локальной CLI и проверяет действующий запуск. Ему
достаточно записи запуска и ведомости. Только после успешной проверки
preflight атомарно сохраняет в закрытом каталоге
`runtime_dir/embedding-attestation.json` с `profile_id`, SHA-256 файла
записи запуска и SHA-256 доверенной ведомости.

Для обычного вызова адаптер проверяет эту аттестацию и привязку к живому
процессу и endpoint до и после отправки запроса. В ответе проверяются
алиас, размерность и конечность компонент. При смене процесса, его записи
или ведомости требуется новый preflight. До него поиск сообщает об ошибке
профиля. `rag_get` продолжает читать SQLite. Изменение параметров из
`embedding_profile`, включая `pooling` и хеш весов, даёт новый `profile_id`.
Присвоение нового запуска старому алиасу не проходит проверку. Все новые
точки одной попытки импорта или перестроения получаются под одной
проверенной записью запуска. Перед коммитом активации версии или поколения
повторно сверяются аттестация, процесс, сокет и профиль. Изменившийся
запуск требует повторной подготовки. Для поиска и публикации в
открытое поколение требуется совместимость с его `profile_id`.
CPU и CUDA могут использовать тот же профиль после успешного
сравнения с общими эталонами. Несовпадение даёт ошибку профиля до
выдачи результата поиска или активации.

CLI `mcp-rag-admin --config PATH --mcp-config PATH` применяет полномочие
`rag.index` из доверенного TOML экземпляра и выполняет локальные операции:

- `init` требует успешный preflight текущего запуска и создаёт схему и
  готовую пустую коллекцию только при первоначальной инициализации.
  Перед коммитом готового поколения команда повторно проверяет ту же
  аттестацию под блокировкой обслуживания.
  Повтор команды с тем же профилем сохраняет готовое поколение и все
  активные версии. При другом профиле команда завершается ошибкой
  несовместимости, а смена профиля выполняется через `rebuild`.
- `exclude --file PATH` отключает указатель версии у источника.
- `rebuild` требует успешный preflight текущего запуска, восстанавливает
  новое поколение по поисковым текстам SQLite с настроенным профилем
  и переключает указатель после проверки.
- `prune-index` получает исключительную блокировку обслуживания
  и удаляет допустимые точки и поколения по
  [правилам публикации](../data-model.md#публикация-исключение-и-восстановление).
  Коллекция готового поколения сохраняется при любом количестве точек.

Каждая команда завершает работу с нулевым кодом при успехе и ненулевым
при ошибке. Подробности диагностики остаются в локальном канале оператора.
