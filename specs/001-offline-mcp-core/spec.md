# Спецификация функции — офлайн-ядро MCP-сервера

**Ветка** `main`

**Создано** 2026-11-20

**Статус** Утверждена

**Утверждено** 2026-11-20

**Исходная задача** Развернуть расширяемый MCP-сервер на машине с локальной
моделью без интернета, подключить проверочный модуль и выполнить сквозной
вызов инструмента из диалога с моделью.
[Конституция v0.3.0](../../.specify/memory/constitution.md)

## Clarifications

### Session 2026-11-20

- Q: Сколько движков из vLLM, llama.cpp и Ollama должны пройти сквозную офлайн-проверку до выпуска первой версии MCP-сервера? → A: Для первой поставки достаточно одного из трёх движков. Конкретный движок выбирается в техническом плане.
- Q: Должны ли клиенты с других машин в локальной сети получать каталог MCP-инструментов и вызывать их уже в первой версии? → A: В первой версии каталог и вызовы MCP доступны только клиентам на машине с сервером.

## Пользовательские сценарии и проверки

### Сценарий 1 — Запустить сервер офлайн (P1)

Оператор переносит подготовленные артефакты на целевую машину и запускает ядро.
Стандартный MCP-клиент подтверждает, что сервер готов принимать запросы.

**Ценность** Оператор может проверить развёртывание отдельно от настройки модели
и установки инструментов.

**Независимая проверка** На чистой целевой машине с отключённым доступом к интернету
развернуть ядро из подготовленного комплекта и запросить каталог инструментов.

1. При первом запуске с пустым списком модулей и остановленным движком модели
   MCP-клиент успешно получает пустой каталог.
2. Если необходимого артефакта или конфигурации нет, оператор получает диагностику,
   по которой можно определить, чего не хватает.

### Сценарий 2 — Подключить и проверить модуль (P1)

Разработчик модуля подключает проверочный инструмент через документированный
контракт. Оператор обнаруживает и вызывает инструмент стандартным MCP-клиентом.

**Ценность** Инструменты можно разрабатывать и проверять независимо от ядра и модели.

**Независимая проверка** Подключить подготовленный по документации проверочный
модуль и запустить ядро при остановленном движке модели. Вызвать инструмент
с известным входом.

1. После явного подключения модуля клиент видит имя, описание и схему входа
   инструмента. Корректный вызов возвращает ожидаемый результат. Для подключения
   модулю достаточно опубликованного контракта и штатной настройки сервера.
2. При неверных аргументах клиент получает ошибку по правилам MCP, а обработчик
   инструмента не выполняется. При прямом вызове отключённого инструмента клиент
   получает отказ, и инструмент отсутствует в каталоге.
3. Если модуль предоставляет защищённую операцию или доступ к защищённым данным,
   клиент с корректными аргументами и недостаточными полномочиями получает отказ
   до выполнения операции или выдачи данных.
4. При ошибке обработчика клиент получает ошибку инструмента. В проверке таймаута
   клиент получает ошибку по истечении лимита, пока тестовый обработчик всё ещё
   задержан. После каждого из этих исходов клиент получает каталог и успешно
   вызывает другой проверочный инструмент.
5. При настройках по умолчанию журнал содержит записи об успешном и неуспешном
   вызовах. Записи состоят только из служебных метаданных. Контрольные значения
   из аргументов, результатов и исходных сообщений об ошибках в них отсутствуют.

### Сценарий 3 — Вызвать инструмент из диалога с моделью (P1)

Пользователь работает с локальной моделью через MCP-хост. Хост получает описание
инструмента от сервера, передаёт его модели, выполняет запрошенный моделью вызов
и передаёт результат обратно модели.

**Ценность** Пользователь может выполнять диалог с инструментами на одной машине
без доступа к интернету.

**Независимая проверка** На одной машине с отключённым доступом к интернету
развернуть сервер, движок модели и MCP-хост из перечисленных в инструкции
артефактов в документированном окружении. Выполнить контрольный диалог из инструкции.

1. Хост получает от модели запрос на вызов. Имя инструмента, аргументы и результат
   наблюдаемого MCP-вызова совпадают с ожидаемыми в контрольном диалоге. Хост
   передаёт фактический результат этого вызова в следующий запрос к той же модели
   и получает ответ.
2. Если движок модели останавливается, ошибка обращения к модели видна в хосте.
   Стандартный MCP-клиент по-прежнему получает каталог и вызывает инструмент
   без модельной зависимости.
3. Оператор воспроизводит сценарий для каждой заявленной конфигурации по инструкции
   с версиями движка и хоста, моделью, настройками обоих соединений и перечнем
   необходимых артефактов.
4. При настройках интеграции по умолчанию локальный запрос к HTTP API модели
   проходит. Сетевой клиент на другой машине с маршрутом к целевой машине
   не может подключиться к этому API.
5. MCP-клиент на машине с сервером получает каталог и вызывает инструмент.
   При сетевом транспорте клиент с другой машины в локальной сети не может
   получить каталог или вызвать инструмент. При несетевом транспорте проверяется
   отсутствие сетевой точки подключения к MCP.

### Граничные случаи

- Два модуля объявляют одинаковое имя инструмента. Сервер явно сообщает о конфликте
  при регистрации. Имя инструмента однозначно указывает на зарегистрированный
  обработчик в рабочей конфигурации.
- Клиент запрашивает неизвестный инструмент или передаёт некорректный MCP-запрос.
  Клиент получает ошибку соответствующего вида по правилам MCP.
- В выбранной конфигурации модель отвечает без запроса инструмента. Для приёмки
  сквозного сценария требуется наблюдаемый MCP-вызов и передача результата модели.

## Требования

### Функциональные требования

- **FR-001**. Развёртывание из подготовленных артефактов, первый запуск и штатная
  работа ядра и включённых модулей должны выполняться без доступа к интернету.
  Инструкция перечисляет необходимые артефакты и шаги для офлайн-развёртывания.
  При отсутствии обязательного артефакта или параметра диагностика развёртывания
  должна дать оператору возможность определить недостающий элемент.
- **FR-002**. Ядро должно запускаться с пустым списком модулей. Стандартный MCP-клиент
  должен получать пустой каталог, в том числе при остановленном движке модели.
- **FR-003**. Разработчик должен иметь возможность явно подключить новый модуль
  через документированный контракт без изменения ядра. Модуль предоставляет имя,
  описание, схему входа и обработчик каждого инструмента. Дублирующее имя вызывает
  ошибку регистрации с указанием конфликтующего имени.
- **FR-004**. Сервер должен публиковать инструменты, доступные запрашивающему
  клиенту, и выполнять их через стандартные операции MCP. Как минимум один
  проверочный инструмент должен принимать входные данные и возвращать результат,
  который можно сверить с ожидаемым. Этот инструмент должен работать без модели.
- **FR-005**. Сервер должен проверять аргументы и доступность инструмента при каждом
  вызове до передачи управления обработчику. Модуль должен проверять полномочия
  клиента перед выдачей защищённых данных или выполнением защищённой операции.
  Полномочия определяются доверенной конфигурацией или проверенным контекстом клиента.
- **FR-006**. Сервер должен сообщать об ошибке обработчика или истечении лимита времени
  как об ошибке инструмента. При истечении лимита сервер должен вернуть ошибку
  независимо от завершения обработчика. После сбоя он должен обслуживать каталог
  и вызовы других инструментов. Ошибки протокола сообщаются по правилам MCP.
- **FR-007**. Диагностические журналы должны содержать записи об успешных и
  неуспешных вызовах. По умолчанию записи о вызовах в журналах ядра и модулей
  должны содержать только служебные метаданные.
- **FR-008**. Сервер и движок должны работать на одной машине. HTTP API модели
  в настройках интеграции по умолчанию доступен только внутри этой машины.
  В первой поставке каталог и вызовы инструментов MCP должны быть доступны
  только клиентам на машине с сервером. Для каждой заявленной конфигурации
  инструкция должна перечислять предпосылки, переносимые артефакты и настройки
  подключения хоста к MCP-серверу и к локальному HTTP API модели.
- **FR-009**. Минимум для приёмки интеграции в первой поставке — одна конфигурация
  с вызовом инструмента, проверенная офлайн на vLLM, llama.cpp или Ollama.
  Конкретный движок определяется в техническом плане. Для каждой заявленной
  конфигурации инструкция должна указывать версии движка и хоста, модель,
  существенные настройки и проверенные возможности. Инструкция должна включать
  контрольный диалог, ожидаемые имя инструмента, аргументы и результат, а также
  способ проверить передачу фактического результата модели. При смене конфигурации
  среди поддерживаемых имена и схемы MCP-инструментов должны сохраняться.

### Ключевые сущности

- **Модуль** — явно подключаемый набор инструментов и их обработчиков.
- **Инструмент** — опубликованные имя, описание, схема входа и поведение при вызове.
- **Вызов инструмента** — выбранный инструмент, аргументы и результат либо ошибка.
- **Конфигурация интеграции** — конкретная связка версий движка и MCP-хоста, модели,
  настроек обоих соединений и подтверждённых возможностей работы с инструментами.

## Критерии успеха

### Измеримые результаты

- **SC-001**. На чистой целевой машине без интернета и без запущенной модели
  оператор по инструкции завершает первое развёртывание и получает каталог из
  нуля инструментов.
- **SC-002**. Разработчик подключает один проверочный модуль по опубликованному
  контракту без изменений ядра, видит его инструмент в каталоге и получает
  ожидаемый результат без запущенной модели.
- **SC-003**. Оба проверочных сбоя возвращают ошибку инструмента. При таймауте
  ошибка получена, пока тестовый обработчик всё ещё задержан. После каждого сбоя
  доступны каталог и вызов второго инструмента. В журналах по умолчанию присутствуют
  записи успешного вызова, ошибки обработчика и таймаута. Число контрольных значений
  из входа, результата и исходного текста ошибок в этих журналах равно нулю.
- **SC-004**. Как минимум в одной конфигурации интеграции завершён сквозной
  сценарий. Для каждой заявленной конфигурации он воспроизводится без интернета
  из перечисленных в инструкции артефактов и предпосылок. Наблюдаются ожидаемые
  имя и аргументы MCP-вызова, передача фактического результата модели и ответ модели.
- **SC-005**. При настройках интеграции по умолчанию локальный запрос к HTTP API
  модели успешен. Попытка подключения к этому API с другой машины, у которой
  есть сетевой маршрут к целевой машине, завершается ошибкой соединения.
- **SC-006**. Локальный MCP-клиент получает каталог и успешно вызывает инструмент.
  При сетевом транспорте оба запроса с другой машины, имеющей маршрут к целевой
  машине, завершаются отказом в доступе или ошибкой соединения. При несетевом
  транспорте подтверждается отсутствие сетевой точки подключения к MCP.

## Допущения

- Оператор использует на целевой машине MCP-хост, который обращается к
  локальному HTTP API модели и вызывает инструменты через MCP.
- Хост, движок и веса модели можно подготовить вне целевой машины и перенести
  на неё до проверки. Инструкция описывает, какие артефакты и предпосылки входят
  в документированное окружение.
- Первая поставка включает ядро, проверочный модуль и воспроизводимый сценарий
  интеграции. Целевые движки проекта — vLLM, llama.cpp и Ollama.
- RAG-поиск будет отдельной функцией и воспользуется контрактом модулей.
