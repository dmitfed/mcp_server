# Контракт проверочного MCP-хоста

[План](../plan.md) · [Руководство приёмки](../quickstart.md) · [Модуль v1](module-v1.md)

Проверочная CLI поставляется в wheel проекта. Версия CLI `mcp-core-check --version`
совпадает с версией wheel. Для первого профиля это `0.1.0`.

| Команда | Назначение |
|---|---|
| `mcp-core-check core --empty-config PATH --demo-config PATH` | Запускает два независимых MCP-сеанса и проверяет пустой каталог и успешный вызов `demo_echo` без обращения к модели. |
| `mcp-core-check e2e --config PATH` | Запускает MCP-клиент и сервер, затем выполняет контрольный диалог с моделью. |

Клиент запускает `mcp-core --config PATH --port 0` как дочерний процесс по
абсолютному пути из каталога скриптов текущего Python-окружения. Он читает одну
запись `mcp_url`, проверяет схему `http`,
IPv4-адрес `127.0.0.1`, порт и путь `/mcp`. Клиент SDK подключается по
Streamable HTTP, подтверждает редакцию `2026-07-28` и capability `tools` через
discovery. Общий лимит запуска в 10 секунд отсчитывается по монотонным часам
с момента перед созданием дочернего процесса до успешного discovery, включая
получение адреса. При временном отказе соединения после объявления адреса хост
повторяет discovery в пределах того же лимита, пока процесс жив. Отклонённый или
несовместимый ответ, выход процесса или истечение лимита завершают запуск с ошибкой.
Хост закрывает HTTP-клиент, завершает и собирает дочерний процесс при любом исходе
проверки. Уборка процесса выполняется отдельно от лимита запуска.

HTTP модели использует отдельный фиксированный адрес `127.0.0.1:9931` и путь
`/v1/chat/completions` с ограничением ожидания 120 секунд на запрос. Для обеих
loopback-связей хост обходит прокси и отклоняет HTTP-переадресацию.

## Контрольный диалог

1. Найти `demo_echo` в реальном `tools/list`. Преобразовать имя, описание и схему
   в описание HTTP-инструмента `type: function`. Передать единственный инструмент
   под именем, полученным из MCP.
2. Запросить модель `qwen3-4b` с сообщением
   `Call demo_echo once with text "mcp-check-001", then report its result.`
   Параметры первого запроса — `stream: false`, `temperature: 0`,
   `seed: 42`, `max_tokens: 128`, `tool_choice: "required"`.
3. В `choices[0].message.tool_calls` требуется один вызов с непустым `id`,
   именем `demo_echo` и аргументами `{"text":"mcp-check-001"}`. После успешного
   MCP-вызова клиент проверяет полученный объект `{"echo":"mcp-check-001"}`.
4. Во второй HTTP-запрос входят исходное сообщение пользователя, фактическое
   сообщение assistant с `tool_calls` и сообщение с `role: "tool"`, исходным
   `id` вызова в поле `tool_call_id` и JSON полученного MCP-объекта в `content`.
   CLI проверяет корреляцию и показывает в приёмочном выводе отправленный объект.
   Второй запрос использует `tool_choice: "none"` и те же остальные
   параметры. Успех — финальный ответ с непустым текстом.
5. Неожиданный ответ, ошибка MCP или недоступность модели завершают проверку
   ненулевым кодом и кратким описанием этапа. Критерий успеха включает обе
   HTTP-фазы и реальный MCP-вызов.

Приёмочный вывод относится к контрольным синтетическим значениям. Журналы
ядра при том же прогоне используют поля из [контракта сервера](server-mcp.md).
