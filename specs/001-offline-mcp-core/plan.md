# План реализации — офлайн-ядро MCP-сервера

**Ветка** `main` · **Дата** 2026-11-20 · **Вход** [утверждённая спецификация](spec.md)

## Резюме

Реализовать Python-процесс MCP-сервера, который запускается офлайн с пустым
каталогом, подключает модули по локальным манифестам и обслуживает их через
Streamable HTTP на loopback. Проверочный MCP-хост запускает сервер отдельным
процессом и подключается к его endpoint `/mcp`. Для модели хост отдельно
обращается к llama.cpp по loopback HTTP и передаёт фактический результат MCP-вызова.

## Технический контекст

| Область | Решение |

| Язык и версия | Python ≥ 3.13 (`requires-python = ">=3.13"`). Базовая офлайн-приёмка использует системный CPython 3.13 в Debian 13. |
| Основные зависимости | `mcp==2.3.0`, `jsonschema==4.26.0`, Uvicorn и стандартная библиотека. Все зависимости фиксируются в lock-файле для целевого интерпретатора. |
| Протоколы | MCP `2026-07-28` через Streamable HTTP, `http://127.0.0.1:<порт>/mcp`. HTTP модели `127.0.0.1:9931/v1/chat/completions`. |
| Хранилище | TOML-конфигурация и JSON-манифесты на диске. Реестр и состояние вызовов в памяти. |
| Тестирование | `unittest`, клиент SDK через реальный loopback HTTP в дочерний MCP-процесс, отдельная офлайн-приёмка с моделью. |
| Целевая платформа | Debian 13, x86-64 (amd64), CPU. Для первого прогона закладываем 8 ГиБ ОЗУ и фиксируем фактическое окружение. |
| Тип проекта | Один Python-пакет с CLI сервера и CLI приёмки. |
| Ограничения | Локальная машина, пакетная офлайн-установка, лимит инструмента 10 с по умолчанию. |
| Объём | Ядро, совместимый манифест, проверочный модуль, одна подтверждённая конфигурация с моделью. |

Профиль приёмки — llama.cpp v1.0.0 (`b12359`) и `Qwen3-4B-Q4_K_M.gguf`
с проверочной CLI `mcp-core-check` версии `0.1.0`. Решения обоснованы в
[исследовании](research.md). Метка поддержки появляется после приёмки.

## Проектирование

### Ядро и вызов

1. CLI читает TOML, валидирует манифесты и строит реестр до входа в цикл MCP.
   Каталог доступен через SDK и при пустом реестре. Конфликт имени завершает
   регистрацию с диагностикой конфигурации.
2. Сервер открывает IPv4-сокет только на `127.0.0.1` и передаёт его Uvicorn.
   ASGI-приложение SDK обслуживает `/mcp` в stateless-режиме с JSON-ответами.
   Для HTTP проверяются `Host` и `Origin`. Прокси-заголовки отключены.
3. Диспетчер проверяет доступность имени и вход по JSON Schema, формирует контекст
   из локальной конфигурации и применяет лимиты допуска.
4. Диспетчер запускает процесс обработчика без shell. Родитель ожидает ответ по
   монотонному дедлайну. При таймауте он возвращает ошибку MCP, игнорирует поздний
   ответ и передаёт завершение и сбор процесса фоновому супервизору. Слот
   освобождается после сбора процесса. Завершение сервера собирает оставшиеся процессы.
5. MCP-сообщения идут через HTTP. В stdout сервера при запуске выводится одна
   запись с локальным адресом. В stderr идут безопасные диагностические записи
   и метаданные вызова. Сырые журналы доступа Uvicorn, вывод обработчиков
   и текст исключений исключены из диагностического потока.

### Интеграция и офлайн-приёмка

1. Проверочная CLI запускает сервер с `--port 0`, читает выделенный порт и
   проверяет готовность через MCP discovery. Затем она использует описание
   `demo_echo` из каталога для запроса модели через её отдельный loopback HTTP.
   Хост завершает и собирает процесс сервера при любом исходе проверки.
2. CLI наблюдает MCP-вызов по имени и аргументам, получает результат и передаёт
   его в продолжение того же диалога. Возврат результата проверяется по
   содержимому второго запроса и идентификатору вызова.
3. Для офлайн-прогона фиксируются базовый образ с перечнем системных пакетов
   и отдельный переносимый комплект. Комплект включает wheel, зависимости,
   конфигурации, манифест, тесты приёмки и контрольные суммы. Движок и GGUF
   подготавливаются по зафиксированным версиям и хешам.
4. [Руководство приёмки](quickstart.md) описывает холодный офлайн-прогон, ошибки
   инструментов, проверку журналов и локальную границу MCP и API модели.

Пути исходников и команды описывают будущую реализацию. Один пакет разделяет
ответственность ядра и проверочного хоста, при этом хост подключается к серверу
через MCP как отдельный клиент.
