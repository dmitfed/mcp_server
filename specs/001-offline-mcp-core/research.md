# Исследование — офлайн-ядро MCP-сервера

Документ фиксирует решения для [плана](plan.md). Версии и возможности сверены по
первоисточникам. Поддержка сквозной конфигурации подтверждается приёмкой на целевой машине.

## Python и локальный MCP

**Решение** Python ≥ 3.13 на Debian 13 x86-64 (amd64), официальный Python SDK
`mcp==2.3.0`, редакция MCP `2026-07-28` и Streamable HTTP через Uvicorn.
Базовая приёмка использует системный CPython 3.13. Сервер строит ASGI-приложение
из низкоуровневого `Server` SDK с явными обработчиками каталога и вызова.
Хост запускает сервер на порту, выделенном ОС, и подтверждает готовность через
MCP discovery по объявленному адресу `http://127.0.0.1:<порт>/mcp`.

**Обоснование** SDK ведёт обмен MCP и разделяет протокольные ошибки и результаты
вызова. Обработчик каталога регистрируется даже при пустом списке модулей.
Привязка к loopback сохраняет утверждённую границу доступа. Проверки `Host`
и `Origin` применяют требования HTTP-транспорта и защищают локальный endpoint
при обращении из браузера. [Debian 13](https://www.debian.org/releases/trixie/release-notes/whats-new.en.html) · [Релиз SDK](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.3.0) · [Версии протокола SDK](https://py.sdk.modelcontextprotocol.io/protocol-versions/) · [Streamable HTTP](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http) · [Проверки заголовков SDK](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/server/transport_security.py)

**Рассмотренные варианты** Фиксированный порт подходит для ручного запуска.
Для запуска клиентом порт `0` и передача уже привязанного сокета Uvicorn позволяют
параллельно запускать экземпляры без конфликта портов. Низкоуровневый SDK даёт
ядру явно публиковать схемы внешних модулей и контролировать результат вызова.
[Низкоуровневый сервер SDK](https://py.sdk.modelcontextprotocol.io/advanced/low-level-server/) · [Реализация SDK v2.3.0](https://github.com/modelcontextprotocol/python-sdk/blob/v2.3.0/src/mcp/server/lowlevel/server.py) · [Программный запуск Uvicorn](https://github.com/Kludex/uvicorn/blob/0.38.0/uvicorn/server.py)

## Модули, схемы и таймаут

**Решение** Конфигурация TOML перечисляет доверенные локальные модули. JSON-манифест
версии `1` объявляет инструменты и пути к обработчикам. Ядро проверяет манифест и
аргументы через `jsonschema==4.26.0`, Draft 2020-12, с локальным разрешением ссылок.
Обработчик выполняется в отдельном дочернем процессе на вызов. Ядро возвращает
результат по монотонному дедлайну, а вывод, завершение и сбор процесса контролирует
отдельно. Базовые параметры — 10 секунд на вызов, 4 одновременно занятых процесса,
ограничение частоты 10 допущенных вызовов в секунду с начальным запасом в 4 вызова.

**Обоснование** Манифест доступен до импорта кода, поэтому каталог и проверка
аргументов сохраняют независимость от обработчика. Раздельное выполнение позволяет
вернуть таймаут, пока синхронный обработчик задержан. Граница процесса также
позволяет отделить журналы и исключить произвольный вывод модуля из MCP-канала.
MCP-результат содержит структурированный объект либо фиксированный код и безопасное
сообщение об ошибке. [MCP Tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) · [Разрешение ссылок JSON Schema](https://python-jsonschema.readthedocs.io/en/stable/referencing/) · [Python asyncio](https://docs.python.org/3.13/library/asyncio-task.html#timeouts) · [Дочерние процессы asyncio](https://docs.python.org/3.13/library/asyncio-subprocess.html)

**Рассмотренные варианты** Импорт и выполнение обработчиков внутри ядра проще для
кооперативных корутин. `asyncio.wait_for` ждёт окончания отмены, а отмена ожидания
потока не останавливает его синхронную работу. Постоянный пул уменьшает затраты
старта и требует отдельного жизненного цикла и замены зависших исполнителей.
Один процесс на вызов выбран для первой версии с короткими инструментами. Контракт
манифеста и MCP позволяет впоследствии изменить механизм исполнения.

## Первая конфигурация с моделью

**Решение** Кандидат на приёмку на Debian 13 amd64 — `llama.cpp v1.0.0 (b12359)`
(CPU), `Qwen3-4B-Q4_K_M.gguf` от Qwen и проверочная CLI `mcp-core-check` версии
`0.1.0`. Клиент работает по Streamable HTTP с MCP-сервером и по HTTP с
`127.0.0.1:9931/v1/chat/completions`. Точный запуск и проверка приведены в
[quickstart](quickstart.md), порядок передачи результата — в [контракте хоста](contracts/acceptance-host.md).

**Обоснование** Движок и модель переносятся как архив и один файл GGUF. Имя архива
содержит `ubuntu`, поскольку так названа сборка CPU от издателя. Её загрузка
системных библиотек и работа на Debian 13 проверяются через `ldd`, запуск бинарника
и офлайн-диалог на целевой системе. Версия
движка поддерживает явные офлайн-параметры, шаблон инструментов и режимы
`tool_choice` для контролируемого диалога. Проверочная CLI использует MCP SDK и
HTTP-клиент стандартной библиотеки. Это позволяет закрепить версию хоста вместе
с проектным wheel и наблюдать результат именно выполненного MCP-вызова.

**Рассмотренные варианты** Ollama поддерживает цикл вызовов через `/api/chat`,
а офлайн-перенос модели использует предварительно заполненный каталог моделей.

## Офлайн-установка и проверка

**Решение** Собираем wheel проекта и полный каталог wheel на Debian 13 amd64
для версии целевого CPython. Базовый комплект рассчитан на CPython 3.13. Фиксируем
версии и SHA-256 в `requirements.lock`. В комплект
входят конфигурация, локальный манифест, тесты для приёмки ядра, архив движка, GGUF
и ведомость контрольных сумм. На цели создаём новый `venv`, устанавливаем строго
из wheelhouse и выполняем `pip check`. Системный образ с Python, `venv`, системными
библиотеками и утилитами фиксируется как подготовленная предпосылка.

**Обоснование** Переносимый комплект проверяется на чистом окружении. Установка
с `--no-index --only-binary=:all: --require-hashes` фиксирует источники и исключает
сборку зависимостей на целевой машине. Для проверок ядра достаточно `unittest`
и отдельного клиентского процесса, а реальный движок нужен для SC-004 и SC-005.
[pip — локальные пакеты](https://pip.pypa.io/en/stable/user_guide/#installing-from-local-packages) · [Проверка хешей pip](https://pip.pypa.io/en/stable/topics/secure-installs/#hash-checking-mode) · [Python venv](https://docs.python.org/3.13/library/venv.html)

**Рассмотренные варианты** Контейнер фиксирует окружение ценой дополнительного
рантайма и переноса образа. Готовый виртуальный Python environment привязан к
путям исходной машины. Перенос wheelhouse с созданием окружения на цели достаточен
для выбранной платформы.
