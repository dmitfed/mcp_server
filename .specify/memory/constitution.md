# Конституция MCP-сервера

Проект конституции открыт для обсуждения. Цель — предоставить расширяемый MCP-сервер
инструментов, который работает без доступа к интернету на одной машине с vLLM,
llama.cpp или Ollama.

## Основные принципы

### I. Границы MCP и инференса

Сервер обязан публиковать и выполнять инструменты через стандартные операции
поддерживаемой редакции MCP. Приложение, выполняющее роль MCP-хоста, управляет
диалогом с моделью и вызывает инструменты через MCP-клиент. Доступ к модели
через локальный HTTP API инференса и доступ к инструментам через MCP — отдельные
интерфейсы. Размещение MCP-хоста и транспорт MCP определяются в спецификации
интеграции.

Ядро обязано запускаться с пустым списком модулей и возвращать пустой каталог
в ответ на `tools/list`. Каталог и вызовы инструментов, которым не нужен инференс,
должны работать при недоступности бэкенда модели.

### II. Контракт модулей

Инструменты добавляются через явную регистрацию модулей по документированному
контракту. Для каждого инструмента модуль предоставляет имя, описание, схему входа
и обработчик. Ядро публикует инструменты и передаёт вызовы обработчикам.
Принцип считается выполненным, если новый модуль подключается через этот контракт
без изменения кода ядра. При дублировании имени регистрация должна завершаться
явной ошибкой.

### III. Проверяемая совместимость с бэкендами

Целевые бэкенды — vLLM, llama.cpp и Ollama. Для каждой заявленной конфигурации
обязательно указать версию бэкенда, модель, существенные настройки и проверенные
возможности HTTP-интеграции. Смена бэкенда сохраняет имена и схемы MCP-инструментов.
Если модулю нужна модельная операция, он явно объявляет эту зависимость и сообщает
о её недоступности через контракт ошибок инструмента.

### IV. Валидация и доступ

Ядро обязано проверять аргументы по опубликованной схеме и применять настройки
доступности инструмента при каждом вызове. Модуль обязан проверять полномочия
клиента до выдачи данных или выполнения защищённой операции. Полномочия определяются
доверенной конфигурацией или проверенным контекстом клиента. Текст от модели,
аргументы вызова и содержимое найденных документов обрабатываются как данные.

### V. Совместимость публичных контрактов

Опубликованные интерфейсы модулей, имена инструментов и семантика их схем должны
сохранять обратную совместимость в рамках поддерживаемой версии. Несовместимое
изменение требует новой версии затронутого контракта и описания миграции.
Ошибки протокола и ошибки выполнения инструмента сообщаются по правилам
поддерживаемой редакции MCP.

### VI. Автономное развёртывание

В целевом развёртывании MCP-сервер и движок модели размещаются на одной машине.
HTTP API инференса по умолчанию доступен только внутри этой машины. Развёртывание,
первый запуск и штатная работа ядра и включённых модулей должны выполняться без
доступа к интернету. Способ развёртывания должен позволять заранее подготовить и
перенести на целевую машину пакеты, веса моделей, конфигурацию и другие необходимые
артефакты.

## Будущий модуль RAG-поиска

RAG-поиск подключается через общий контракт модулей. Структурированный результат
содержит найденные фрагменты и для каждого — ссылку или идентификатор, по которому
можно проверить источник. Ограничения доступа действуют и на фрагменты, и на их
метаданные. Пустая выдача означает, что поиск успешно завершился среди доступных
источников. Сбой поиска сообщается как ошибка выполнения инструмента.

Базовый сценарий RAG выполняется на локальном корпусе без доступа к интернету.
Документы и все необходимые для поиска данные доступны на целевой машине,
включая индекс и веса модели эмбеддингов, если они используются. Хост решает,
как использовать найденные данные при запросе генерации. Форматы источников и
выдачи, способ индексации, эмбеддинги, хранилище и ранжирование определяются
в спецификации RAG.

## Проверка изменений

- Проверка ядра стандартным MCP-клиентом покрывает пустой каталог, обнаружение и
  вызов тестового инструмента без модели, отказ при невалидных аргументах и отказ
  при прямом вызове отключённого инструмента.
- Заявленная поддержка каждого сочетания бэкенда, модели и настроек подтверждается
  сквозной проверкой на реальном бэкенде на той же машине. Для режима с инструментами
  проверяется путь от обнаружения инструмента через MCP до передачи результата
  вызова обратно модели.
- Офлайн-проверка покрывает развёртывание из заранее подготовленных артефактов,
  первый запуск и сквозной сценарий с отключённым доступом к интернету и доступным
  локальным HTTP API модели.
- При появлении RAG проверяются происхождение фрагментов, ограничения доступа, пустая
  выдача и сбой зависимости, если поиск использует отдельную службу. Поиск по
  локальному корпусу входит в офлайн-проверку.

## Управление изменениями

После утверждения конституция задаёт обязательные требования для спецификаций,
планов и ревью. При изменении публичного контракта в ревью указываются затронутые
принципы, влияние на совместимость и проверки, подтверждающие результат.

Поправка описывает причину, влияние на существующие контракты, необходимую миграцию
и требует утверждения владельцем проекта. Версия следует SemVer. Уровень `MAJOR`
используется для несовместимого изменения или удаления обязательного принципа,
`MINOR` — для добавления принципа или расширения требований, `PATCH` — для уточнений,
сохраняющих смысл норм.
